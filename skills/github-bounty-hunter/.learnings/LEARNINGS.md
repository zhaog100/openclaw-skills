## 2026-04-29 近期实战经验总结（04-26 至 04-29）

### 🔴 严重教训（必须记住）

#### 1. 网络不稳定是最大敌人
- **场景**: 2026-04-29 下午，VS Code Extension 推送连续失败
- **表现**: `gnutls_handshake() failed: The TLS connection was non-properly terminated`
- **影响**: 400 RTC 任务卡在本地无法提交（#2890, #2867, #2864, #2868）
- **教训**:
  - 大任务（多文件 PR）必须在网络稳定时执行
  - 开发过程中频繁 `git commit`，避免堆积
  - 推送失败时不要死循环重试，等 5-10 分钟再试
  - 准备好 SSH 推送作为备选方案（`git@github.com:` 格式）
- **预防措施**:
  - 任务开始前先 `ping github.com` 测试网络
  - 每完成一个子任务就 commit，不要攒到一起
  - 配置 SSH 远程作为 HTTPS 的备选

#### 2. GitHub Token 过期导致工作中断
- **场景**: 2026-04-08 Token 失效，所有 gh 命令失败
- **影响**: 无法查询 PR 状态、提交代码、创建 Claim Issue
- **教训**: Token 有效期有限（通常 30-90 天），需要定期检查
- **预防措施**:
  - 每周检查一次 Token 有效性：`gh auth status`
  - 建立 Token 轮换提醒机制
  - Token 失效后第一时间 `gh auth login --web` 重新授权

#### 3. 付款流程不熟悉导致延迟收款
- **场景**: RustChain PR #2205 合并后 9 天才创建 Claim Issue
- **影响**: 2 RTC 逾期 9 天，#2165 和 #2205 同样延迟
- **教训**:
  - RustChain 付款流程：PR 合并 → **立即**创建 Claim Issue → 等待付款
  - 不要等！Claim Issue 越早创建越早拿到钱
  - Claim Issue 格式要规范（参考 Issue #2129 教训）
- **预防措施**:
  - PR 合并后 1 小时内创建 Claim Issue
  - 使用标准化的 Claim Issue 模板
  - 监控已合并 PR，超时未创建 Claim 则告警

### ⚠️ 重要教训（影响效率）

#### 4. 批量提交 ≠ 高效
- **场景**: homelab-stack 15 个 PR 全部提交后，审核全部排队
- **表现**: 维护者审核速度慢，PR 积压
- **教训**:
  - 批量提交会造成审核瓶颈
  - 分散提交（每天 2-3 个）比一次性提交 15 个更好
  - 等待审核反馈后再提交下一批
- **改进**: 控制节奏，最多同时开放 5-8 个 PR

#### 5. 支付方式检查必须在认领前完成
- **场景**: 部分任务未明确支付方式就开始开发
- **影响**: 完成开发后发现不支持自己的收款方式，白做
- **教训**:
  - 认领任务前必须检查 Issue 中的支付方式
  - 确认支持 USDT(TRC20)、RTC、或其他已有钱包的方式
  - 支付方式不明确的任务降低优先级
- **预防措施**:
  - 扫描后先运行 `payment_checker.py`
  - 支付方式不支持 → 跳过
  - 支付方式不明确 → 先评论询问维护者

#### 6. 大任务开发需要分段验证
- **场景**: AgentFolio #2890 开发中，demo video 生成失败（安全过滤器拦截）
- **影响**: 整个 Claim 被阻塞
- **教训**:
  - 大任务分解为独立可交付的子任务
  - 每完成一个子任务就测试验证
  - 高风险环节（视频生成、API 调用）先做 POC
- **改进**: 开发流程改为：POC → 核心功能 → 文档 → 可选内容

#### 7. 技能文件删除必须分析依赖
- **场景**: 历史中误删 `full-auto-pipeline.py`
- **影响**: auto 命令失效
- **教训**:
  - 删除任何文件前 `grep -r` 搜索引用
  - 建立文件依赖图
  - 删除前先备份（`trash` > `rm`）

### 💡 正面经验（继续保持）

#### 8. 高质量 PR 比数量重要
- **数据**: homelab-stack 8 个 PR 全部通过审核，0 被拒绝
- **原因**:
  - 完整的文档 + 测试 + 配置文件
  - 通过 shellcheck 验证
  - 生产级代码质量
- **结论**: 做少而精，每个 PR 都要做到无可挑剔

#### 9. 自动化扫描 + 人工筛选是最佳组合
- **实践**: 技能自动扫描 + AI 人工筛选评分 > 50 的任务
- **效果**: 避免了低价值任务浪费时间
- **结论**: 阈值调整：≥$100 → >$10（含 RTC > 10）

#### 10. 知识库和记忆系统很重要
- **实践**: 每日回顾 + 知识库更新 + MEMORY.md 精简
- **效果**: 跨会话知识延续，避免重复学习
- **结论**: 每天至少一次回顾，重要发现立即记录

## 2026-04-29 新增规则（强制执行）

### 规则 1：网络检查优先
```
开始任何开发任务前：
1. ping github.com -c 3（延迟 < 500ms 才算正常）
2. gh auth status（确认 Token 有效）
3. git remote -v（确认远程配置正确）
```

### 规则 2：支付检查优先
```
认领任务前：
1. 运行 payment_checker.py 检查支付方式
2. 确认支持 USDT(TRC20) 或 RTC
3. 确认钱包地址已配置
4. 支付方式不支持 → 跳过
```

### 规则 3：Claim Issue 即时创建
```
RustChain PR 合并后：
1. 1 小时内创建 Claim Issue
2. 使用标准化模板
3. 附上 PR URL + 合并时间
4. 48 小时未付款 → 礼貌提醒
```

### 规则 4：分段提交策略
```
同时开放的 PR 数量：
- 最多 5-8 个
- 等待审核反馈后再提交下一批
- 不要一次性提交 10+ 个 PR
```

### 规则 5：任务阈值
```
扫描过滤条件：
- USDT/USDC: >$10
- RTC: >10
- 低于阈值 → 跳过（除非特别简单）
```
